# 《掌心乡野》《拓印小铺》——发布与技术适配审查

本文件对应 2026-10-29 两款微信小游戏的 v5/v6 设计讨论，是**工程适配与验收建议**，不是已实现功能报告。

## 一、共同结论

- 两款当前以自由组合、无强制标准答案为核心；这份发布 Skill **不能直接提高游戏可玩性、开发建筑/印章引擎或自动生成美术素材**。
- Skill 的作用应当从**首个可玩原型完成之后**逐步增加：工程审计 → 构建适配 → 资源治理 → 真机回归 → 上传开发版。
- 不必为了迁就 Skill 强制选择 Cocos。若确定使用 Cocos Creator，可直接复用其构建导出流程；若采用 Canvas/WebGL、其他引擎，需先验证对应的微信小游戏适配工具链。
- 以最低端目标 Android 手机的真实帧率、内存峰值、触控延迟和冷启动作为发布门禁；不可用桌面模拟器代替。

## 二、掌心乡野：发布风险与测试

**设计核心**：可重复组合的房间体量（建议 24×24 初始构建区域、最多 3 层，均为待验证初值），屋顶、门窗、阳台、院墙、植物和地表；房屋可保存、复制、拆分。

优先验证：
1. 长屋、L/U 形、错层的合法拼接；墙面/屋顶自动更新后与玩家编辑状态一致。
2. 房体移动时门窗及附着物随动；删除带上层依赖的房体必须预览影响，撤销可完整恢复。
3. 俯视下选中被遮挡墙面、楼层隐藏/恢复，以及不同纵横比手机的屏幕操作。
4. 低端机在多房间、多植物、不同材质下的 Draw Call、纹理尺寸、帧率、内存；必要时使用图集、实例复用和地表分块。
5. 保存→完全退出→重开后，部件 ID、归属关系、层级、屋面分区、房屋组合都与保存前一致。

发布优化方向：静态房屋装饰合图，材质复用，场景可见性裁剪，低成本阴影/光照，远处对象简化与按需加载。不要为了减包直接破坏可编辑部件数据。

## 三、拓印小铺：发布风险与测试

**设计核心**：基础章、主题章、纹样章自由重复、缩放、镜像、变色、叠加及组合保存；可进入图层修改并撤销。

优先验证：
1. 同一印记在编辑预览、压印完成、保存重开、导出图片四个阶段的变换保持一致。
2. 纹样裁入真实不透明色面并保留内部孔洞，图层移动和组合变换后仍正确。
3. 复制/缩放/旋转组合章、拆分和撤销不会产生重复引用或丢失宿主关系。
4. 印章数量增加时的重绘时间、纹理缓存、撤销栈上限及高分辨率导出内存峰值。
5. 未开启声音、离线、切后台、重启后仍可以创作和恢复未完成作品。

发布优化方向：可复用印章资源、缓存静态图层、限制不必要的离屏画布分辨率、采用可恢复的增量操作日志；不使用强混淆影响图层与序列化调试。

## 四、推荐实施顺序

- P0：先完成各自的最小可玩原型。不要先安装复杂混淆插件。
- P1：验证 Cocos/其他引擎到微信游戏工程的构建输出及真机启动。
- P2：建立包体、冷启动、帧率、存档回归测试与发布资料清单。
- P3：取得独立上传授权后提交开发版本，后台核对；提审、正式发布另外确认。

**重要**：当前未在可访问的 GitHub 仓库清单中发现明确以这两款游戏命名的实际源码仓库，因此不能声称完成了项目接入、真机测试或上传。
